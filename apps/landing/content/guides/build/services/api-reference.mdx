# Agent API Reference

The Agent API accepts typed Intents and returns ordered `EventPage`s. Actions
are durable Events with typed `Action.request` and `ActionResult` unions. Current transaction execution also exposes durable Commit views in `EventPage.commits`; do not treat every transaction as an Action.

## Start turn

```http
POST /v1/agent/chat
Authorization: Bearer <exact Agent resource token>
Content-Type: application/json
Idempotency-Key: <unique operation key>
```

```json
{
  "sessionId": "session-uuid",
  "message": "What is my ETH position worth?",
  "mode": "direct",
  "app": "default",
  "userState": {
    "connection": {
      "is_connected": true,
      "provider": "para"
    },
    "evm": {
      "address": "0x0000000000000000000000000000000000000001",
      "chain_id": 8453
    }
  }
}
```

The response is the first ordered page:

```json
{
  "session_id": "session-uuid",
  "cursor": "opaque-cursor",
  "has_more": false,
  "events": [
    {
      "type": "turn_state_changed",
      "event_id": "event-uuid",
      "turn_id": "turn-uuid",
      "sequence": 1,
      "occurred_at": 1787184000000,
      "state": "processing"
    }
  ]
}
```

## Poll Events

```http
GET /v1/agent/chat/{sessionId}?cursor={opaqueCursor}&wait=25000
```

All client-visible messages, lifecycle changes, tools, tasks, notices, errors,
titles, and Actions share the same monotonically ordered sequence. Do not
decode or synthesize cursors. On a typed invalid/expired cursor error, retry
without `cursor` to hydrate from the ledger.

## Respond to an Action

```http
POST /v1/agent/chat/{sessionId}/actions/{actionId}/result
Authorization: Bearer <exact Agent resource token>
Content-Type: application/json
Idempotency-Key: <unique operation key>
```

```json
{
  "revision": 1,
  "result": {
    "status": "rejected",
    "reason": "Rejected by user"
  }
}
```

The backend validates Action ownership, revision CAS, expiry, idempotency, and
request/result compatibility before appending the new Action revision and
resuming the turn.

A durable transaction's `CommitView.version` tracks its chain lifecycle.
The optional `continuation` tracks assistant delivery separately: its `version`
is the schema version, while `revision` orders delivery updates. Older servers
may omit `revision`, which clients treat as zero. A confirmed transaction can
still have a pending or retrying continuation; that does not authorize another
wallet submission.

## Interrupt

```http
POST /v1/agent/chat/{sessionId}/interrupt
Authorization: Bearer <exact Agent resource token>
Content-Type: application/json
Idempotency-Key: <unique operation key>
```

```json
{
  "turnId": "turn-uuid"
}
```

The response is an `EventPage` containing the resulting lifecycle transition.

## Session metadata

```text
GET    /v1/agent/sessions
GET    /v1/agent/sessions/{sessionId}
PATCH  /v1/agent/sessions/{sessionId}
DELETE /v1/agent/sessions/{sessionId}
```

These routes own list metadata such as title and archive state. They are not a
second transcript or lifecycle authority.

## Pipeline

The `/v1/pipeline/*` surface is stateless. It discovers operations and carries portable version 2 Builds through stage, simulate, and explicit commit. Commit revalidates the Build and returns the legacy `status: "committed"` label plus `preparation_status: "prepared"`, `digest`, `provider_invoked: false`, and `requests: ActionRequest[]`. These have no durable Agent Action IDs. The caller submits them with its wallet and tracks receipts.

Use `/v1/agent/mcp` for Agent MCP and `/v1/pipeline/mcp` for Pipeline MCP, each with its own exact-resource OAuth grant. Read the [canonical API reference](https://aomi.dev/docs/api-reference/overview) and the selected origin's `/openapi.json`; source, npm, and deployments can differ during a release.
