# Provider sign-in carrier conflict

The stale-session fix from PR #709 was present on staging and worked: the live
page had no active Aomi account session, but a fresh Para provider exchange
still returned `already_linked_to_another_account` with a wallet collision.

The provider auth plugin selected its Better Auth carrier with the provider's
verified real email. When that email already belonged to a historical Better
Auth user for another canonical account, account resolution saw that carrier
owner before the provider's verified wallets and failed closed. Clearing the
browser cache could not change this deterministic server lookup. Privy used
the same path.

Provider exchanges now select a synthetic `@accounts.invalid` carrier email
derived from the verified provider, issuer environment, tenant, and subject.
The real verified email remains available to canonical account resolution, so
genuine identity conflicts still fail closed. Regression coverage exercises
both Para and Privy and proves a real-email carrier is not reused. The account
package version is 0.2.9. No deployment was performed.
